## 발견 사항

### 1. 공개 DCR 등록 한도를 영구 소진할 수 있음 — 중간, 가용성

위치: `mcp-oauth/gateway.py:93`.

`/register`는 미인증 클라이언트 등록을 허용하고, 등록 레코드는 사실상 만료하지
않습니다. 전체 등록 수가 1,000개이면 신규 등록이 거부됩니다. 승인받지 않은 등록도
같은 한도를 사용합니다. 속도 제한은 있지만 총량 누적은 막지 못합니다.

격리 DB에 1,000개 등록을 넣고 prune 후에도 1,000개가 유지됨을 확인했습니다.
다음 정상 등록은 HTTP 400으로 거절됐습니다. 운영에서 한도 소진은 실행하지 않았습니다.
영향은 새 앱/새 사용자 연결 불가이며, 기존 등록과 이미 발급된 토큰이 즉시
무효화되는 문제는 아닙니다. 현재는 수동 DB 정리가 필요합니다.

권장: 미승인·미사용 클라이언트에 만료와 정리를 적용하고 승인된 클라이언트와
별도 한도를 사용합니다. 신뢰할 수 있는 요청 출처별 DCR 제한과 운영자의 연결
관리·폐기 수단도 추가합니다.

### 2. 익명 요청이 정상 로그인·토큰 갱신의 속도 제한을 소진함 — 중간, 가용성

위치: `mcp-oauth/gateway.py:184`.

등록·authorize·token·revoke가 전역 `auth` 버킷(분당 120회)을 공유합니다.
로그인 POST도 전역 버킷(5분당 15회)을 사용하며 유효하지 않은 flow 요청도
한도를 소비합니다. 요청 출처나 실제 클라이언트를 구분하지 않습니다.

격리 앱에서 익명 authorize 요청 이후 정상 refresh가 429로 거절됐습니다.
잘못된 flow 로그인 요청 이후에도 정상 로그인·승인이 429로 거절됐습니다.
공격이 반복되면 정상 사용자의 재인증과 갱신을 계속 방해할 수 있습니다.

권장: 익명 등록·로그인과 인증된 클라이언트의 토큰 갱신을 분리합니다. 신뢰할 수
있는 프록시 경계에서 확인한 출처와 계정/클라이언트별 제한을 병행하며, 전역 제한은
최후의 자원 보호용으로 둡니다. 임의의 X-Forwarded-For 헤더를 곧바로 신뢰하면 안 됩니다.

### 3. `/mcp/`에서 HTTPS→HTTP 리다이렉트 — 중간, 전송 보호

위치: `mcp-oauth/gateway.py:439`, `deploy/Caddyfile.oauth.tailscale`.

실제 공개 응답:

```http
GET https://cognee.wegle.com/mcp/
HTTP/2 307
Location: http://cognee.wegle.com/mcp
```

별도 확인한 `http://cognee.wegle.com/mcp`는 HTTPS로 301 리다이렉트합니다.
하지만 클라이언트가 중간 HTTP 요청을 보내면 그 구간은 TLS로 보호되지 않습니다.
307을 따르는 방식과 헤더 제거 여부는 클라이언트에 따라 달라집니다.
실제 자격증명이 HTTP로 유출된 것은 이번 점검에서 관찰하지 않았습니다.
정확한 `/mcp` 경로는 정상적으로 HTTPS 401을 반환합니다.

권장: `/mcp/`도 인증된 MCP 핸들러로 직접 처리하거나 HTTPS로만 정규화합니다.
외부 TLS 종료 환경에서 자동 생성되는 리다이렉트의 scheme을 검증합니다.
확인한 공개 응답에는 HSTS도 없으므로 HTTPS 처리 수정 후 HSTS 적용을 검토합니다.

### 4. 인증 코드 재사용 감지 후 기존 발급 토큰을 유지함 — 낮음, 방어 보완

위치: `mcp-oauth/gateway.py:124`, `mcp-oauth/gateway.py:140`.

격리 앱에서 인증 코드를 한 번 교환하고 같은 코드를 다시 제출하면 400으로
거절됩니다. 하지만 최초 교환으로 발급된 access/refresh 토큰은 계속 유효합니다.
사용한 코드를 삭제해 발급 토큰 묶음과의 연관 정보를 보존하지 않기 때문입니다.

PKCE가 적용되어 있으므로 인증 코드만 안다고 교환할 수 있는 취약점은 아닙니다.
코드·verifier 등이 함께 탈취된 상황에서 재사용 감지를 통한 추가 차단이 부족합니다.
[RFC 9700 §4.2.4](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.2.4)은
코드 중복 교환 시 그 코드로 발급된 기존 토큰도 폐기하도록 권고합니다(SHOULD).

권장: 사용한 코드의 해시와 token family 연관 정보를 제한된 기간 보존하고,
해당 코드의 재사용 감지 시 관련 토큰을 폐기합니다.

## 정상 확인 사항

- 미인증 GET/POST, 잘못된 Bearer, Basic, 가짜 로그인 쿠키, query token 모두 401.
- `/health`, `/docs`, `/openapi.json`, `/.env`, `/.git/config`, `/api/v1/datasets`는
  공개 경로에서 404. OAuth metadata 공개는 의도한 동작입니다.
- S256 PKCE, client ID·redirect URI·resource·scope 검증과 만료 처리 회귀 테스트 통과.
- 로그인 Origin·쿠키·소유자 계정·비밀번호·명시적 승인 검사 통과.
- refresh rotation, 교체된 refresh 재사용 시 token family 폐기, 명시적 revoke 검사 통과.
- OAuth/MCP 자격증명과 로그인 쿠키를 MCP upstream에 전달하지 않는 검사 통과.
- OAuth 컨테이너는 비 root, privileged=false, Linux capability 전체 제거, 호스트 공개 포트 없음.
- Caddy/REST/UI의 호스트 포트는 loopback 바인딩. DB 포트의 호스트 공개 없음.
- OAuth 상태 디렉터리 0700, DB 0600, deploy/.env와 UI 자격증명 파일 0600.
- 인증서 검증 성공. 점검 클라이언트는 TLS 1.2와
  ECDHE-ECDSA-CHACHA20-POLY1305를 협상했으며 인증서 만료는 2027-02-06입니다.
  이는 TLS 1.3 지원 여부나 모든 TLS 설정을 전수 검사했다는 의미는 아닙니다.

## 잔여 운영 위험

기존 MCP_TOKEN은 호환성을 위해 계속 허용됩니다. 만료·개별 앱별 폐기·OAuth 로그인
보호가 이 토큰에는 적용되지 않으므로 유출 시 별도 교체가 필요합니다. `memory`
scope는 개인 메모리 전체의 검색·저장·삭제 권한이며 읽기 전용 또는 데이터셋별
격리를 제공하지 않습니다. 이 서버를 다중 사용자 격리 서비스로 사용하면 안 됩니다.

권장 수정 순서: HTTPS 리다이렉트 → 전역 속도 제한 분리 → 미사용 DCR 만료·정리 →
인증 코드 재사용 시 토큰 폐기. 수정 후 이번 재현 사례를 회귀 테스트에 추가합니다.
